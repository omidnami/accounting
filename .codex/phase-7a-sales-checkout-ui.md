# Phase 7A: رابط فروش و صندوق

وضعیت: تکمیل شد

## هدف

ساخت و تأیید فاکتور فروش چندردیفی از رابط فارسی و راست‌چین، بدون پیاده‌سازی
مجدد منطق انبار، بهای تمام‌شده یا اسناد حسابداری.

## تصمیم‌های معماری

- همه تغییرات نهایی از `SalesService` عبور می‌کنند.
- ایجاد فاکتور idempotency دارد؛ ارسال دوباره همان فرم فاکتور جدید نمی‌سازد.
- idempotency request hash مانع استفاده همان token برای داده متفاوت می‌شود.
- جست‌وجوی مشتری و کالا async و محدود به فروشگاه/انبار جاری است.
- موجودی نمایش‌داده‌شده در POS مربوط به انبار انتخاب‌شده است.
- پیش‌نویس فاکتور قابل حذف است؛ فاکتور تأییدشده قابل حذف یا ویرایش نیست.
- نقش‌های مدیر، حسابدار و صندوق‌دار به رابط فروش دسترسی دارند.
- خروج انبار، COGS، مطالبات، مالیات و سند فقط هنگام تأیید نهایی ثبت می‌شوند.

## پیاده‌سازی

- `SalesInvoiceController`: فهرست، ایجاد، نمایش، تأیید و حذف پیش‌نویس.
- `SalesLookupController`: lookup محدود و سبک مشتری و کالا.
- `SalesInvoiceRequest` و `ConfirmSalesInvoiceRequest`.
- `SalesCheckoutLookupService`.
- idempotency در `SalesService` و migration فاکتورها.
- صفحه `sales/Index` با جست‌وجو، وضعیت و آمار.
- صفحه `sales/Create` با جست‌وجوی async، ردیف‌های قابل ویرایش، تخفیف،
  مالیات، موجودی انبار و کنترل سمت کلاینت.
- صفحه `sales/Show` با اقلام، جمع‌ها، انبار تأیید، چاپ و حذف پیش‌نویس.
- helper مشترک نرمال‌سازی ارقام فارسی/عربی برای فرم‌های کالا و فروش.

## اصلاح جانبی موجودی

- مقایسه chronology حرکت انبار به «روز بعد» تغییر کرد تا حرکت همان‌روز در
  SQLite به‌اشتباه آینده محسوب نشود؛ مقایسه همچنان در MySQL index-friendly است.

## تست

- کنترل دسترسی مهمان، انباردار و نقش‌های مجاز.
- lookup مشتری محدود به فروشگاه.
- lookup کالا با موجودی انبار انتخاب‌شده و جست‌وجوی بارکد فارسی.
- ساخت پیش‌نویس، محاسبه تخفیف/مالیات و idempotency.
- رد استفاده همان token برای درخواست متفاوت.
- تأیید فاکتور، خروج موجودی و سند متوازن.
- جلوگیری از تأیید دوباره.
- حذف فقط پیش‌نویس.
- فهرست و فیلتر وضعیت.

نتیجه نهایی:

- Pest: 154 تست موفق، 836 assertion
- PHPStan: صفر خطا
- Pint: موفق
- Vue type-check و build: موفق
- migration idempotency روی MySQL اجرا شد.

## اصلاحات بازبینی

- مجوز `canManageSales` برای ساخت پیش‌نویس و مجوز `canConfirmSales` برای تأیید
  نهایی از هم جدا شدند.
- صندوق‌دار پیش‌نویس می‌سازد، اما تأیید نهایی فقط برای مدیر و حسابدار نمایش
  داده می‌شود.
- صفحه جزئیات برای صندوق‌دار وضعیت «در انتظار تأیید» نمایش می‌دهد.
- خطاهای اعتبارسنجی مقدار، قیمت، تخفیف و مالیات هر ردیف مستقیماً زیر فیلد
  همان ردیف نمایش داده می‌شوند.
- تست ایجاد پیش‌نویس صندوق‌دار، رد تأیید او و تأیید نهایی مدیر اضافه شد.
- تست خطاهای هم‌زمان مقدار و مالیات ردیف اضافه شد.

## محدودیت و گام بعد

- دریافت نقدی/بانکی و تخصیص آن به فاکتور در UI این مرحله نیست.
- انتخاب تاریخ هنوز با input میلادی انجام می‌شود؛ تاریخ‌نمای شمسی در UI
  تکمیل نشده است.
- برگشت از فروش و چاپ حرارتی/دستگاه POS در این برش نیست.
- بررسی دستی مرورگر انجام نشده؛ شواهد UI شامل type-check و build است.
- پیشنهاد گام بعد: رابط دریافت مشتری، تخصیص پرداخت به فاکتور و نمایش وضعیت
  تسویه/مانده فاکتور.
