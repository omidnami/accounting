# بخش ۱ — معماری سرور و دیتابیس

## ۱.۱ تصمیم‌های پایه

1. هر دو محصول از **یک کدبیس** استفاده می‌کنند.
2. هر tenant یک **دیتابیس مستقل** دارد.
3. دیتابیس مرکزی فقط اطلاعات کنترل پلتفرم را نگه می‌دارد.
4. tenant با subdomain قبل از authentication شناسایی می‌شود.
5. connection دیتابیس tenant در runtime تنظیم می‌شود؛ `.env` جدا ساخته نمی‌شود.
6. app server بدون state دائم tenant اجرا می‌شود.
7. ایزولاسیون داده در سطح دیتابیس است؛ افزودن اجباری `tenant_id` به همهٔ
   جدول‌های مالی لازم نیست.
8. cache، session، queue، فایل، log و backup باید tenant-aware باشند.
9. نصب مستقل از همان هستهٔ tenancy استفاده می‌کند، اما control plane را غیرفعال
   می‌کند.

## ۱.۲ واژه‌ها

| مفهوم | معنا |
|---|---|
| Tenant | سازمان مشتری در راست‌چین |
| Central Database | دیتابیس مدیریت tenantها، پلن‌ها و provisioning |
| Tenant Database | دیتابیس کامل حسابداری یک tenant |
| Store | فروشگاه یا کسب‌وکار داخل tenant |
| Branch | شعبهٔ یک Store |
| Standalone | نصب مستقل برای یک مشتری |
| Rastechin | نصب چندمستأجری روی یک کدبیس |
| Profile | پریست تنظیمات یک صنف |
| Module | قابلیت اختیاری با منطق و schema مستقل |
| Plan | بستهٔ تجاری شامل Profile، Module، محدودیت و پشتیبانی |

`store_id` جای `tenant_id` را نمی‌گیرد. یک tenant ممکن است در آینده چند Store یا
شعبه داشته باشد.

## ۱.۳ توپولوژی هدف

```text
                         مشتری / مرورگر
                               │
                     DNS + Wildcard TLS
                               │
                    WAF / Load Balancer
                               │
              ┌────────────────┴────────────────┐
              │                                 │
       App Serverهای stateless          Queue Workerها
              │                                 │
       ┌──────┴────────┐                       │
       │               │                       │
 Central MySQL     Tenant MySQLها          Redis / Queue
       │               │
       │               └── Database جدا برای هر tenant
       │
 Object Storage / Backup / Monitoring
```

اجرای اولیه می‌تواند روی یک MySQL server با databaseهای جدا باشد. فیلد `db_host`
در رکورد مرکزی tenant امکان انتقال بعدی tenantهای بزرگ به سرور جداگانه را
فراهم می‌کند.

### حالت Standalone

```text
App Server → Tenant Database مشخص‌شده در .env
```

دیتابیس مرکزی، provisioning و پنل مدیریت SaaS غیرفعال است. همان مدل‌ها،
migrationها و سرویس‌های tenant استفاده می‌شوند.

### حالت Rastechin

```text
admin.example.com → Central Database
tenant.example.com → Tenant Database همان tenant
```

## ۱.۴ دیتابیس مرکزی

حداقل داده‌های پیشنهادی:

| جدول/دامنه | محتوا |
|---|---|
| `tenants` | شناسه، نام، وضعیت، پلن، زمان ایجاد و تعلیق |
| `tenant_domains` | subdomain یا دامنهٔ اختصاصی، tenant و وضعیت تأیید |
| `tenant_database_connections` | host، نام دیتابیس، کاربر و رمز رمزنگاری‌شده |
| `tenant_subscriptions` | پلن، شروع، پایان، وضعیت پرداخت |
| `tenant_modules` | ماژول‌های مجاز، فعال و نسخهٔ نصب‌شده برای هر tenant |
| `tenant_profiles` | پروفایل صنفی و نسخهٔ اعمال‌شده |
| `provisioning_jobs` | وضعیت ساخت tenant، خطا و retry |
| `migration_runs` | وضعیت migration هر tenant در هر release |
| `platform_admins` | مدیران سیستم، جدا از کاربران tenant |
| `module_catalog` | ماژول‌های منتشرشده و سازگاری آن‌ها |

رمز دیتابیس tenant نباید plaintext ذخیره یا در log ظاهر شود.

## ۱.۵ دیتابیس tenant

تمام جداول فعلی حسابداری داخل این دیتابیس قرار می‌گیرند:

- کاربران همان کسب‌وکار
- حساب‌ها و اسناد
- سال مالی و دوره
- طرف‌حساب‌ها
- کالا، انبار و موجودی
- خرید، فروش و مرجوعی
- دریافت، پرداخت و چک
- POS
- گزارش‌ها و Audit
- جدول‌های ماژول‌های فعال همان tenant

به دلیل ایزولاسیون فیزیکی، uniqueهای فعلی مثل شمارهٔ فاکتور یا کد کالا می‌توانند
در همان دیتابیس یکتا بمانند.

## ۱.۶ چرخهٔ یک درخواست tenant

```text
درخواست به tenant.example.com
        ↓
ResolveTenant Middleware
        ↓
خواندن tenant از Central Database
        ↓
بررسی دامنه، وضعیت active و اشتراک
        ↓
تنظیم runtime connection به نام tenant
        ↓
Purge اتصال قبلی و ست‌کردن connection پیش‌فرض
        ↓
Authentication روی Tenant Database
        ↓
Controller / Service / Report روی همان دیتابیس
        ↓
ثبت tenant ID در log و context
        ↓
Reset اتصال و context در پایان request/job
```

نکتهٔ حیاتی: tenant باید **قبل از auth** resolve شود. کاربران tenant در دیتابیس
مرکزی وجود ندارند.

دامنهٔ ناشناس، tenant تعلیق‌شده یا در حال provisioning نباید به برنامهٔ مالی
دسترسی پیدا کند.

## ۱.۷ قواعد تنظیم اتصال دیتابیس

- تنظیمات پایه در `config/database.php` باقی می‌ماند.
- connection مرکزی و tenant از هم جدا هستند.
- اطلاعات tenant می‌تواند در Redis کش شود، اما شامل رمز plaintext نباشد.
- purge اتصال قبل از تغییر تنظیمات اجباری است.
- connection پیش‌فرض فقط بعد از resolve موفق tenant تغییر می‌کند.
- connection مدیریتی ساخت دیتابیس نباید در runtime عمومی در دسترس باشد.
- user دیتابیس هر tenant فقط روی database خودش دسترسی داشته باشد.
- چرخش رمز، تعلیق یا تغییر دیتابیس باید cache را بی‌اعتبار کند.

### PHP-FPM، Queue و Octane

در PHP-FPM هر request محیط تازه‌ای دارد. در queue worker و Laravel Octane، state
بین اجراها باقی می‌ماند. بنابراین reset tenant در این نقاط اجباری است:

- پایان HTTP request
- پیش از هر queue job
- پایان queue job
- scheduled task
- Artisan command مرتبط با tenant

هر job باید `tenant_id` داشته باشد و connection را خودش دوباره initialize کند.

## ۱.۸ provisioning یک tenant

```text
ثبت tenant با وضعیت pending
        ↓
ساخت database و user با کمترین دسترسی
        ↓
ذخیرهٔ اطلاعات رمزنگاری‌شده در Central Database
        ↓
اجرای migrationهای هسته روی Tenant Database
        ↓
اجرای Profile Seederهای هسته
        ↓
ساخت Store، Branch، سال مالی و کاربر مدیر اول
        ↓
اعمال Profile صنفی و Moduleهای انتخابی
        ↓
تغییر وضعیت tenant به active
```

قواعد:

- provisioning داخل queued job اجرا شود، نه داخل HTTP request.
- job idempotent و قابل retry باشد.
- tenant نیمه‌ساز active نشود.
- خطای هر مرحله ثبت و برای مدیر سیستم قابل مشاهده باشد.
- در صورت شکست، دیتابیس ناقص طبق سیاست نگه‌داری یا پاک‌سازی شود.
- ساخت کاربر مدیر اول فقط در همین مسیر مجاز باشد.

## ۱.۹ سرویس‌های tenant-aware

| بخش | قاعده |
|---|---|
| Session | cookie domain دقیق tenant یا cookie name جداگانه |
| Cache | prefix یا store مستقل tenant |
| Queue | tenant ID در payload و initialize مجدد در worker |
| Scheduler | fan-out jobها به tenantهای فعال |
| File Storage | disk یا path مستقل tenant |
| Log | tenant ID در context |
| Rate Limit | کلید مستقل tenant |
| Backup | backup و restore مستقل هر Tenant Database |
| Report مرکزی | pipeline تحلیلی جدا؛ join مستقیم بین DBها ممنوع |
| Notification | تنظیمات و ارسال در context همان tenant |

Session مشتری A نباید به subdomain مشتری B نشت کند. مدیر مرکزی نیز guard و
session جداگانه داشته باشد.

## ۱.۱۰ امنیت

- Wildcard DNS و Wildcard TLS برای subdomainها.
- allowlist دامنهٔ اصلی و جلوگیری از Host Header Injection.
- رمز اتصال tenantها با کلید برنامه رمزنگاری شود.
- دسترسی CREATE/DROP DATABASE فقط برای فرایند provisioning.
- tenant rate limit و محدودیت مصرف منابع داشته باشد.
- log نباید credential یا دادهٔ حساس مالی را بی‌هدف ثبت کند.
- backupها رمزنگاری و دسترسی محدود داشته باشند.
- Central Database نقطهٔ حساس است و backup و monitoring جداگانه می‌خواهد.

## ۱.۱۱ انتشار نسخه و migration

```text
Deploy کد
    ↓
Backup از tenantهای تحت تأثیر
    ↓
ارسال job migration به tenantهای فعال
    ↓
ثبت نتیجهٔ موفق/ناموفق برای هر tenant
    ↓
فعال‌سازی نسخهٔ جدید برای tenantهای موفق
```

قواعد:

- migrationهای destructive با الگوی expand/contract انجام شوند.
- tenant در حال migration موقتاً read-only شود.
- rollback هر tenant مستقل باشد.
- نسخهٔ schema هر tenant در Central Database ثبت شود.
- seederهای هسته و ماژول فقط روی tenant مربوطه اجرا شوند.
- migration tenant هرگز روی Central Database اجرا نشود و برعکس.

## ۱.۱۲ Backup و بازیابی

- Central Database و همهٔ Tenant Databaseها backup داشته باشند.
- backup هر tenant مستقل قابل restore باشد.
- restore یک tenant نباید tenant دیگر را متوقف کند.
- بازیابی باید روی محیط آزمون تست شود، نه فقط وجود گزینهٔ backup.
- retention، مالکیت داده و حذف نهایی tenant باید سیاست مستند داشته باشند.

## ۱.۱۳ فاصلهٔ پروژهٔ فعلی از این معماری

پروژه فعلی single-tenant است. مهم‌ترین کارهای لازم:

- افزودن Central Database و مدل tenant
- شناسایی tenant از subdomain
- dynamic connection و reset امن
- provisioning queue‌شده
- tenant-aware کردن session، cache، queue، فایل و log
- دستور rollout migration برای همهٔ tenantها
- تفکیک مدیر مرکزی از کاربر tenant
- backup/restore مستقل tenant
- پشتیبانی از حالت Standalone بدون control plane

در این مدل لازم نیست همهٔ queryها با `tenant_id` فیلتر شوند؛ ایزولاسیون اصلی
فیزیکی است. اما `tenant_id` در job، cache، فایل، log و رکورد مرکزی الزامی است.

## ۱.۱۴ معیار پذیرش معماری سرور

1. دو tenant با دیتابیس جدا بدون دسترسی متقابل کار کنند.
2. login هر tenant فقط کاربران دیتابیس خودش را ببیند.
3. subdomain ناشناس، تعلیق‌شده یا ناقص رد شود.
4. job tenant A بعد از job tenant B روی دیتابیس درست اجرا شود.
5. cache و session بین tenantها نشت نکند.
6. provisioning شکست‌خورده قابل retry و قابل مشاهده باشد.
7. backup و restore یک tenant مستقل آزمایش شود.
8. migration همهٔ tenantها وضعیت قابل گزارش داشته باشد.
9. حالت Standalone بدون Central Database کار کند.
10. credentialها در log، cache و خروجی debug نمایان نشوند.

# بخش ۲ — حسابداری چندصنفی

## ۲.۱ اصل بنیادی

برای هر صنف یک fork جدا ساخته نمی‌شود.

ساختار هدف:

```text
Core Accounting
      │
      ├── Retail Base
      │      ├── Catalog
      │      ├── Inventory
      │      ├── Sales & Purchase
      │      ├── Treasury
      │      └── POS
      │
      ├── Industry Profiles
      │      ├── General
      │      ├── Clothing
      │      ├── Grocery
      │      ├── Mobile & Computer
      │      └── ...
      │
      └── Optional Modules
             ├── Production
             ├── Warranty & Repair
             ├── Advanced Pricing
             ├── Units & Packing
             ├── Marketplace
             └── Payroll
```

از نظر تجاری می‌توان نسخهٔ پوشاک و نسخهٔ خواروبار فروخت؛ از نظر کد باید همان
هسته و همان سرویس‌ها استفاده شوند.

## ۲.۲ تعریف نسخهٔ پایه

نسخهٔ پایه، حداقل حسابداری مورد نیاز مشاغل فروشگاهی و خدماتی است. این فهرست از
صفحهٔ رسمی دشت، راهنمای مستقل حساب‌می، سیستم حسابداری سپیدار و محصول فروشگاهی هلو
استخراج شده است. این فهرست یک استاندارد قانونی ادعا نمی‌شود؛ سنتز نیاز محصول و
الزامات فنی است.

«بستهٔ پایهٔ دشت» با «نسخهٔ پایهٔ حساب‌یار» یکی نیست؛ در دشت برخی قابلیت‌های
ضروری مثل حسابداری دوبل و درخت حساب در افزودنی یا سطح بالاتر قرار دارند.

### Account Pack

Account Pack شامل:

- کد و عنوان حساب
- نوع و ماهیت حساب

- نیاز به طرف‌حساب

قواعد:

- تداخل کد یا کلید منطقی باید قبل از اعمال تشخیص داده شود.

- حذف Module نباید حساب‌های دارای گردش را حذف کند.

## ۲.۸ مدل داده برای چندصنفی

### کالا و خدمت

هسته باید دو نوع آیتم را بشناسد:

- **کالای انباری:** خروج/ورود انبار، ارزش‌گذاری و COGS دارد.
- **خدمت یا کالای غیرانباری:** حرکت انبار و COGS ندارد؛ درآمد، مطالبات و
  مالیات مانند فاکتور استاندارد ثبت می‌شود.

این تفاوت باید با یک سیاست صریح روی آیتم مدیریت شود، نه با شرط‌های پراکنده در
Controller. مسیر فروش و خرید باید برای آیتم غیرانباری، `InventoryService` را
فراخوانی نکند.

وضعیت فعلی پروژه این قابلیت را ندارد: `ProductStockPolicy` فقط `simple` و
`min_max` است و `SalesService` برای هر ردیف فاکتور خروج انبار می‌سازد. بنابراین
پشتیبانی از خدمت یکی از شکاف‌های نسخهٔ پایه است.

### ویژگی کالا

ستون‌های `variant_color` و `variant_size` مخصوص پوشاک‌اند و باید به ویژگی عمومی
تبدیل شوند:

- تعریف ویژگی مانند رنگ، سایز، مدل، برند
- مقدار ویژگی برای هر کالا
- نوع داده: متن، عدد، انتخاب
- قابل استفاده در فیلتر و گزارش

تعریف عمومی ویژگی و مقدار آن بخشی از نسخهٔ پایه است. تنوع پیشرفته، ماتریس
خرید/فروش و ویژگی‌های محاسباتی می‌توانند Module باشند.

### واحد

حداقل نسخهٔ پایه باید این‌ها را داشته باشد:

- واحد پایه
- واحد قابل انتخاب برای کالا یا خدمت
- ذخیرهٔ snapshot واحد در ردیف فاکتور

این قابلیت‌ها Module هستند:

- واحد خرید و واحد فروش با ضریب تبدیل
- تبدیل کارتن به بسته و عدد
- فروش وزنی و اتصال ترازو

یک رشتهٔ سادهٔ `unit` برای همهٔ صنف‌ها کافی نیست، اما نباید همهٔ تبدیل‌های
پیشرفته را به هسته اضافه کرد.

### کانال فروش

مارکت‌پلیس و فروشگاه آنلاین **نوع فاکتور جدید نیستند**؛ کانال فروش‌اند.

- فاکتور نهایی از نوع Sales می‌ماند.
- کانال می‌تواند POS، فروش دستی، آنلاین یا مارکت‌پلیس باشد.
- سفارش بیرونی در جدول ماژول خودش نگه‌داری می‌شود.
- پس از تأیید سفارش، سند فروش استاندارد ساخته می‌شود.

### جدول‌های ماژول

ماژول باید جدول‌های خودش را داشته باشد و از core tableها استفاده کند، نه اینکه
برای هر صنف ستون به جدول‌های مشترک اضافه کند.

## ۲.۹ قرارداد ماژول

هر Module باید این اجزا را در محدودهٔ خودش داشته باشد:

- شناسه و نسخه
- وابستگی‌ها و سازگاری با core
- manifest
- Service Provider
- مدل‌ها و سرویس‌ها
- migration
- seeder مخصوص tenant
- route و controller
- صفحه‌های Inertia/Vue
- permission
- منو و quick action
- Account Pack
- event listener، job و schedule
- گزارش و export
- تست

قواعد وابستگی:

- core هرگز نام Module اختیاری را import نکند.
- Module از قراردادهای عمومی core استفاده کند.
- Module نباید مستقیم سند مالی یا حرکت انبار نهایی بسازد.
- posting از `PostingService` عبور کند.
- movement انبار از `InventoryService` عبور کند.
- عملیات مالی اتمیک و idempotent بمانند.

## ۲.۱۰ چرخهٔ عمر Module

```text
Available
   ↓ Install
Installed
   ↓ Enable for tenant
Enabled
   ↓ Disable
Disabled
   ↓ Upgrade
Enabled / Disabled
   ↓ Uninstall
Removed from catalog
```

در حسابداری:

- Disable فقط عملیات جدید را متوقف می‌کند.
- تاریخچه و سندهای ثبت‌شده باقی می‌مانند.
- Uninstall کد را حذف می‌کند، نه دادهٔ مالی.
- Purge داده اقدام جداگانه‌ای بعد از retention و نبود ارجاع مالی است.

## ۲.۱۱ بسته‌بندی Module — تصمیم باز

پیشنهاد اولیه:

- Moduleهای داخلی به‌صورت modular monolith یا local Composer package.
- نصب و upgrade کد فقط توسط اپراتور/CI.
- مدیر tenant فقط Moduleهای از پیش تأییدشده را فعال یا غیرفعال کند.
- آپلود ZIP شامل PHP توسط مدیر tenant مجاز نباشد.

اگر در آینده ZIP لازم شد:

- فقط deployment-time
- امضاشده و checksum‌دار
- با backup، maintenance mode، staging و rollback
- نه به‌عنوان قابلیت عادی مدیریت tenant

این موضوع هنوز تصمیم نهایی ندارد.

### تصمیم‌های حاصل از مقایسه

1. پشتیبانی از **کالای انباری و خدمت/کالای غیرانباری** بخشی از نسخهٔ پایه است.
2. تعریف عمومی ویژگی و واحد پایه در هسته می‌ماند؛ تبدیل پیشرفتهٔ واحد Module است.

4. tenancy و Module Engine پیش از راه‌اندازی راست‌چین باید تکمیل شوند.
5. وابستگی POS به هسته باید قبل از استخراج POS رفع شود.
6. اسناد و گزارش‌های ثبت‌شده هر Module باید پس از غیرفعال‌سازی یا حذف کد باقی
   بمانند.

- دفتر حرکت، ارزش‌گذاری و COGS برای کالای انباری
- شمارش و انتقال پایهٔ انبار
- دریافت، پرداخت، صندوق، بانک، کارت و چک
- POS پایه
- مالیات پایه و اطلاعات VAT
- گزارش‌های مالی و عملیاتی پایه
- Audit، نقش‌ها و امنیت
- backup/restore و first-run setup

### قواعد

- هیچ fork صنفی ساخته نشود.
- فروش خدمت یا کالای غیرانباری نباید حرکت انبار یا COGS بسازد.
- قابلیت‌های آینده در جدول‌های core speculative اضافه نشوند.
- معیار پذیرش نسخهٔ ۱ همان معیارهای `.codex/PROJECT-CONTEXT.md` باشد.

### معیار خروج

- چرخهٔ کامل خرید تا بستن دوره تست شود.
- فروش کالا و فروش خدمت هر دو بدون خطای انباری ثبت شوند.
- گزارش‌ها با اسناد تطبیق داده شوند.
- CI، امنیت، backup و پذیرش UI تکمیل شود.
- نصب تازه فقط از مسیر first-run انجام شود.
- هسته بدون هیچ Module اختیاری قابل اجرا باشد.

## مرحلهٔ ۲ — پروفایل‌های صنفی

هدف: یک کد، چند تجربهٔ صنفی.

### محتوا

- Profile Manifest/Seeder
- نام و ترتیب منوها
- پیش‌فرض ویژگی‌ها و واحدهای مناسب صنف
- Account Pack پروفایل
- قالب فاکتور و گزارش
- onboarding صنفی
- دادهٔ نمونه
- تصمیم دربارهٔ Moduleهای پیشنهادی هر پروفایل

ساختار عمومی ویژگی و واحد پایه در مرحلهٔ ۱ ساخته شده است؛ مرحلهٔ ۲ فقط
پیش‌فرض‌ها و تنظیمات صنفی را اعمال می‌کند. تبدیل پیشرفتهٔ واحد و تنوع ماتریسی
در صورت نیاز به Module منتقل می‌شوند.

### پروفایل‌های اولیه

1. عمومی
2. پوشاک
3. خواروبار

این سه پروفایل بیشترین تطابق را با قابلیت‌های فعلی دارند.

### قواعد

- سیدر تنظیمات سفارشی tenant را بازنویسی نکند.
- Profile نسخه‌دار و idempotent باشد.
- تغییر Profile فقط ظاهر و پیش‌فرض‌ها را تغییر دهد، مگر منطق ماژول لازم باشد.
- اعمال Profile روی tenant موجود باید dry-run و تأیید داشته باشد.

### معیار خروج

- همان هسته با سه Profile مختلف اجرا شود.
- تست‌های مالی بین پروفایل‌ها یکسان بمانند.
- نام منو، ویژگی، واحد، قالب و گزارش بدون تغییر کد عوض شوند.
- تنظیمات دستی tenant حفظ شوند.

## مرحلهٔ ۳ — ماژول‌های پایهٔ صنفی

هدف: افزودن فرایندهایی که با تنظیم ساده قابل پیاده‌سازی نیستند.

### ماژول‌های اولیه پیشنهادی

- خواروبار: تبدیل واحد، ترازو و لیبل وزن‌دار
- موبایل/کامپیوتر: ضمانت و خدمات پس از فروش
- نانوایی/شیرینی: تولید و BOM
- پوشاک: تنوع پیشرفته و تخفیف فصلی، در صورت نیاز
- داروخانه: انطباق صنفی، فقط بعد از بررسی حقوقی

### قواعد

- هر Module schema، permission و تست مستقل داشته باشد.
- Module از core service استفاده کند.
- غیرفعال‌سازی Module سندهای ثبت‌شده را از بین نبرد.
- Account Pack بدون تداخل اعمال شود.
- core بدون Module اختیاری تست شود.

### معیار خروج

- نصب، فعال‌سازی، غیرفعال‌سازی و upgrade Module آزمایش شود.
- اسناد Module در گزارش‌های مالی core دیده شوند.
- حذف Module دادهٔ مالی تاریخی را حفظ کند.
- هر Module حداقل در یک Profile واقعی استفاده شود.

## ترتیب توصیه‌شده

```text
تثبیت MVP
    ↓
Profile Engine + پروفایل عمومی
    ↓
پروفایل پوشاک و خواروبار
    ↓
Moduleهای خواروبار، موبایل و تولید
    ↓
ارزیابی صنف‌های regulated
```

معماری tenant را باید پیش از راه‌اندازی راست‌چین تکمیل کرد، اما لزوماً نباید
پیش از انتشار نسخهٔ مستقل انجام شود. هستهٔ tenancy از ابتدا در نظر گرفته شود
تا refactor دوباره لازم نشود.

# تصمیم‌های قطعی این سند

1. هر دو محصول از یک کدبیس و Tenant Database جدا استفاده می‌کنند.
2. برای هر صنف fork کد ساخته نمی‌شود؛ Profile و Module استفاده می‌شود.
3. نسخهٔ پایه هم کالای انباری و هم خدمت/کالای غیرانباری را پشتیبانی می‌کند.
4. ساختار عمومی ویژگی و واحد پایه در هسته است؛ تبدیل پیشرفتهٔ واحد Module است.
5. First-run و Backup/restore قبل از انتشار نسخهٔ ۱ الزامی‌اند.
6. حذف یا غیرفعال‌سازی Module داده و سندهای مالی تاریخی را از بین نمی‌برد.

# تصمیم‌های باز

1. بسته‌بندی Module: داخلی، Composer package یا ZIP امضاشده
2. اولین صنف‌های واقعی بازار پس از عمومی، پوشاک و خواروبار
3. دامنهٔ قانونی و regulated ماژول داروخانه
4. سیاست retention و حذف نهایی Tenant Database
5. topology دقیق MySQL، Redis، Queue و Backup در production
6. اینکه مدیر tenant چه Moduleهایی را مجاز به فعال‌سازی خودکار باشد

# قواعد ادامهٔ کار

1. این سند قبل از طراحی Schema یا Module جدید خوانده شود.
2. هر تصمیم باز با کاربر نهایی شود.
3. تغییر Architecture در همین سند ثبت شود.
4. تا زمانی که مرحلهٔ مربوط تأیید نشده، ماژول یا پروفایل جدید پیاده‌سازی نشود.
5. `.codex/PROJECT-CONTEXT.md` همچنان مرجع وضعیت واقعی پروژه است.
