# حساب‌یار - مستند مرجع پروژه

آخرین به‌روزرسانی: ۲۰۲۶-۱۰-۲۴

## هدف این سند

این سند نقطهٔ شروع کانتکست جدید برای پروژهٔ `accounting-system` است. وضعیت
واقعی پیاده‌سازی، تصمیم‌های قطعی، معماری، مسیر طی‌شده، کارهای باقی‌مانده و نقشهٔ
آینده را یک‌جا نگه می‌دارد.

سند `.codex/retail-accounting-architecture.md` سند پژوهشی اولیه و مرجع چشم‌انداز
محصول، جریان‌های کسب‌وکار، اصول حسابداری و منابع بررسی‌شده است. در تعارض بین
طرح اولیه و وضعیت پیاده‌سازی، این سند و سپس کد و تست‌های جاری منبع حقیقت‌اند.

مسیر پروژه:

```text
/home/omid/Projects/deepseek-agent/accounting/accounting-system
```

## دستور شروع کانتکست جدید

```text
در پروژه accounting-system ادامه بده.
ابتدا .codex/PROJECT-CONTEXT.md و
.codex/retail-accounting-architecture.md را کامل بخوان.
سپس وضعیت Git و تست‌ها را بررسی کن و فقط مرحلهٔ تأییدشده را ادامه بده.
Business logic نباید وارد Controller شود و commit را خودم می‌زنم.
```

## وضعیت کلی

- محصول یک نرم‌افزار حسابداری فروشگاهی متصل به خرید، فروش، انبار، خزانه و
  گزارش‌های مالی است.
- MVP از نظر قابلیت‌های اصلی چرخهٔ کسب‌وکار تقریباً کامل است؛ برداشت دقیق:
  «آمادهٔ پذیرش نهایی»، نه «آمادهٔ فروش بدون تست دستی و production hardening».
- نسخهٔ فعلی محصول و UI تک‌فروشگاهی است. مدل استقرار هدف، یک نسخهٔ مستقل با
  دیتابیس و در صورت نیاز هاست مستقل برای هر مشتری است.
- شعبهٔ فنی پیش‌فرض `MAIN` وجود دارد، اما چندشعبه‌ای در نسخهٔ فعلی ارائه
  نمی‌شود.
- کارمندان در سطح فروشگاه تعریف می‌شوند و در نسخهٔ فعلی تخصیص شعبه ندارند.
- بررسی دستی کامل رابط کاربری، تست امنیتی مستقل و acceptance چاپگر واقعی هنوز
  انجام نشده است.

## وضعیت Git و کیفیت

- شاخه: `main`
- آخرین commit کد: `2fc9792` با پیام
  `test(ci): separate MySQL concurrency suite`
- این commit و commit قبلی هنوز ممکن است نسبت به remote جلو باشند؛ وضعیت live
  Git باید در شروع هر کانتکست دوباره خوانده شود.
- مالک commit و push کاربر است. Agent نباید بدون درخواست صریح commit یا push
  انجام دهد.

آخرین نتیجهٔ تأییدشده:

- Pest پیش‌فرض روی SQLite: ۳۱۸ تست موفق، ۲۴۶۹ assertion، بدون skip/Warning.
- Integration روی MariaDB: ۵ تست موفق، ۱۸ assertion، با دو اتصال مستقل و
  `REPEATABLE READ`.
- Pint، PHPStan، Vue type-check و frontend build موفق.
- Node calendar: ۴ تست موفق.
- `composer.json` و `git diff --check` معتبر.

فرمان‌های کیفیت:

```bash
composer ci:check
npm run build
DB_CONNECTION=mysql \
DB_DATABASE=accounting_system_concurrency_test \
composer test:integration
```

Integration فقط روی MySQL/MariaDB معتبر است و از suite پیش‌فرض SQLite خارج شده
است. CI آن را در مرحله‌ای جداگانه اجرا می‌کند.

## تصمیم‌های قطعی محصول

1. MVP تک‌فروشگاهی و تک‌لوکیشنی است.
2. هر مشتری نسخه، دیتابیس و در صورت نیاز هاست مستقل دارد؛ multi-tenancy
   اشتراکی ساخته نمی‌شود.
3. `store_id` مرز داده و `branch_id` سازگاری فنی نسخهٔ بعدی است.
4. همهٔ عملیات فعلی روی شعبهٔ پیش‌فرض `MAIN` اجرا می‌شوند.
5. Routeهای مدیریت و انتخاب شعبه در نسخهٔ فعلی 404 می‌شوند.
6. کارمند فعلاً در سطح فروشگاه است و تخصیص شعبه در نسخهٔ بعدی بررسی می‌شود.
7. ارزش‌گذاری موجودی با میانگین موزون متحرک انجام می‌شود.
8. موجودی منفی ممنوع است.
9. مرجوعی کامل و جزئی خرید و فروش پشتیبانی می‌شود.
10. دریافت و پرداخت می‌تواند به چند فاکتور تخصیص داده شود.
11. سند مالی نهایی فقط از `PostingService` ثبت می‌شود و پس از ثبت قابل ویرایش
    یا حذف مستقیم نیست.
12. سند نهایی فقط برای نقش‌های `manager` و `accountant` قابل تأیید است.
13. سامانه مودیان در MVP پیاده نمی‌شود؛ اطلاعات مالیاتی پایه حفظ می‌شود.
14. چاپ عمومی از پنجرهٔ مرورگر مسیر پیش‌فرض است؛ Print Agent اختیاری برای
    چاپ بی‌صدا در دستگاه مشتری طراحی شده است.
15. سرور ابری نباید مستقیم به چاپگر داخل شبکهٔ خصوصی فروشگاه متصل شود.

## اصول غیرقابل مذاکره

- منطق مالی، دامنه و orchestration در Service یا Model قرار می‌گیرد، نه
  Controller یا Vue.
- هر رویداد مالی قطعی باید سند متوازن بدهکار/بستانکار داشته باشد.
- محاسبات مبلغ و مقدار با `Decimal`/bcmath انجام می‌شود.
- عملیات چندجدولی در transaction انجام می‌شود.
- عملیات حساس باید lock، idempotency یا هر دو داشته باشد.
- سند، فاکتور، دریافت و پرداخت نهایی بدون رخداد کنترل‌شده تغییر نمی‌کنند.
- `inventory_movements` منبع حقیقت انبار است و تغییر موجودی خارج از
  `InventoryService` مجاز نیست.
- تاریخ حرکت انبار نمی‌تواند از آخرین گردش همان کالا و انبار عقب‌تر باشد.
- Store/Branch scope در Query و Service کنترل می‌شود؛ به فیلتر UI تکیه نمی‌شود.
- اطلاعات تاریخی باید snapshot بمانند: قیمت، هزینه، مالیات، COGS و طرف‌حساب.
- هر باگ واقعی مالی، انبار یا هم‌زمانی باید regression test داشته باشد.
- قابلیت‌های مالی بدون تست دامنه‌ای و سناریوی شکست پذیرفته نمی‌شوند.

## معماری دامنه

### حسابداری

- `PostingService` تنها مسیر ساخت و ثبت سند نهایی است.
- `JournalEntry` و `JournalEntryLine` سند و ردیف‌های دوطرفه را نگه می‌دارند.
- توازن با bcmath کنترل می‌شود.
- هنگام ثبت، سال مالی، دورهٔ باز، شعبه، حساب معین فعال و Party دوباره بررسی
  و قفل می‌شوند.
- سند یا ردیف Posted قابل ویرایش و حذف مستقیم نیست.
- سند اختتامیه سالانه سود/زیان را به سود انباشته منتقل می‌کند.
- بازگشایی سال، سند اختتامیه را با سند معکوس بی‌اثر می‌کند.
- گزارش‌های سود و زیان، اختتامیه و معکوس آن را برای جلوگیری از دوباره‌شماری
  حذف می‌کنند.

### سال مالی و دوره

- سال مالی شمسی با ۱۲ دوره، sequence و کنترل هم‌پوشانی ساخته می‌شود.
- دوره می‌تواند نیمه‌بسته یا بستهٔ نهایی شود.
- سند، فاکتور، دریافت و پرداخت باز مانع بستن دوره‌اند.
- ساخت Draft در دورهٔ بسته ممنوع است.
- بازگشایی فقط برای مدیر و با دلیل Audit انجام می‌شود.
- بستن سال نیازمند سال بعد باز و ساختار پیوستهٔ ۱۲ دوره است.

### انبار و بهای تمام‌شده

- منبع حقیقت: `inventory_movements`
- تصویر جاری: `inventory_balances`
- ورود، خروج، انتقال و تعدیل از `InventoryService` عبور می‌کند.
- میانگین موزون متحرک و snapshot هزینهٔ هر خروج پیاده شده است.
- انتقال بین انبارها دو حرکت متناظر اتمیک دارد و سود/زیان ایجاد نمی‌کند.
- Batch و سریال به حرکت انبار متصل‌اند.
- برداشت Batch به روش FEFO انجام می‌شود.
- هشدار Batch منقضی یا نزدیک انقضا ساخته و بسته می‌شود.
- شمارش چندکالایی، Draft/Edit/Post و سند تعدیل دارد.
- تعدیل شمارش کالای سریال‌دار فعلاً با خطای دامنه‌ای مسدود است؛ این محدودیت
  موقت است و تکمیل قابلیت محسوب نمی‌شود.

### کالا

- دسته‌بندی کالا
- کالای والد و تنوع به‌صورت SKU مستقل
- بارکد و واحد
- تاریخچهٔ قیمت خرید و فروش
- نقطه سفارش، موجودی ایمنی، مقدار سفارش، حداکثر موجودی و Min/Max
- Batch، تاریخ تولید/انقضا و سریال
- پیشنهاد مقدار سفارش در کاتالوگ و Dashboard

کاتالوگ فعلاً سراسری است و `products.store_id` ندارد. این تصمیم برای MVP
پذیرفته شده است، اما پیش از multi-tenancy اشتراکی یا مقیاس چندفروشگاهی باید
دوباره بررسی شود.

### خرید

- Draft، تأیید، ورود انبار، بدهی تأمین‌کننده و سند خرید
- taxes و هزینه‌های جانبی خرید با تخصیص به بهای موجودی
- برگشت خرید
- پرداخت چندفاکتوری
- idempotency فاکتور و پرداخت
- ماندهٔ پرداختنی در `SupplierPayableService` متمرکز است
- پرداخت و مرجوعی هم‌زمان با lock از تخصیص بیش از مانده جلوگیری می‌کنند

### فروش

- Draft، خروج انبار، COGS، درآمد، مالیات، مطالبات و سند فروش
- صندوق‌دار Draft می‌سازد و مدیر/حسابدار تأیید می‌کند
- دریافت چندفاکتوری
- برگشت فروش
- idempotency فاکتور و دریافت
- ماندهٔ دریافتنی در `CustomerReceivableService` متمرکز است
- دریافت و مرجوعی هم‌زمان با lock از تخصیص بیش از مانده جلوگیری می‌کنند

### خزانه و چک

- `TreasuryAccount` به حساب معین دفتر کل متصل است.
- Cash/Bank/Card در دریافت و پرداخت استفاده می‌شوند.
- چک دریافتی و پرداختی، Pending، Collected/Spent و Bounced دارد.
- شماره داخلی چک از sequence و شماره بانکی به‌صورت دستی ثبت می‌شود.
- وصول، خرج و برگشت چک سند و رخداد مستقل دارند.

### مرجوعی

- سقف مرجوعی در ساخت Draft، ویرایش و تأیید کنترل می‌شود.
- مرجوعی‌های قطعی با lock خوانده می‌شوند.
- برگشت خرید بهای خروج انبار را برمی‌گرداند.
- اختلاف قیمت برگشت خرید برابر است با:

```text
مبلغ خالص برگشت - بهای خروج انبار
```

- اختلاف مثبت بستانکار و اختلاف منفی بدهکار است.
- سریالی که قبلاً از یک فاکتور مرجوع شده دوباره برای همان فاکتور قابل انتخاب
  نیست.

### گزارش‌ها

- دفتر روزنامه، دفتر معین، تراز آزمایشی، سود و زیان و ترازنامه
- صورتحساب مشتری/تأمین‌کننده و Aging تاریخی
- فروش روزانه، فروش/سود کالا و COGS
- کاردکس تعدادی و ریالی با حفظ scope کاربر
- تحلیل فروش بر اساس دسته، تنوع، Batch و کالای پرفروش ماه
- CSV سازگار با Excel، XLSX بومی و PDF سمت سرور
- خروجی Audit با حفظ مجوزها و فیلترهای صفحه

### چاپ

- چاپ A4/A5 و حرارتی ۵۸/۸۰ میلی‌متر از مرورگر
- قالب و تعداد نسخه در سطح فروشگاه تنظیم می‌شود
- انتخاب موقت قالب هنگام چاپ فاکتور
- Print Agent محلی با توکن Station، صف Job، claim/complete، TTL و OS spooler
- Agent فقط اتصال خروجی HTTPS دارد و پورت ورودی باز نمی‌کند

پذیرش چاپگر واقعی، بسته‌بندی Agent، Linux/CUPS، Android/Bluetooth و ESC/POS
خام هنوز جزو کارهای آینده‌اند.

### کاربران، امنیت و Audit

- نقش‌ها و محدودیت‌های اصلی در Backend اعمال می‌شوند.
- Audit Log و صفحهٔ مدیریت کاربران وجود دارد.
- حذف آخرین مدیر سیستم مسدود است.
- 2FA زیرساخت دارد.
- غیرفعال‌سازی کاربر، reset کنترل‌شدهٔ 2FA، retention و alerting کامل Audit
  هنوز باقی مانده است.

- چندشعبه‌ای تعویق افتاده است.
- مدیریت بیش از یک انبار از UI کامل نیست.
- تعدیل شمارش سریال‌دار هنوز پیاده نشده است.
- کاتالوگ در MVP جهانی است و فروشگاه‌محور نیست.
- ویرایش/لغو مستقل چک و گزارش اختصاصی چک هنوز کامل نیست.
- لینک بارگذاری مجدد فرم‌ها و برخی بهبودهای جزئی UX باقی مانده‌اند.
- سامانه مودیان خارج از MVP است.
- اتصال فروشگاه آنلاین، مارکت‌پلیس و درگاه پرداخت وجود ندارد.

### کیفیت

- تست خودکار خوبی برای سناریوهای مالی، انبار و هم‌زمانی وجود دارد.
- تست‌های UI، accessibility، browser compatibility و visual regression هنوز
  سیستماتیک نیستند.
- تست‌های هم‌زمانی باید روی MySQL/MariaDB اجرا شوند؛ SQLite شاهد معتبر نیست.

## تعریف پذیرش نسخهٔ ۱

نسخهٔ ۱ زمانی آمادهٔ تگ‌خوردن است که همهٔ موارد زیر شاهد داشته باشند:

1. نصب تازه از صفر فقط از مسیر first-run انجام شود.
2. یک چرخهٔ کامل خرید، فروش، دریافت، پرداخت، مرجوعی، شمارش و بستن دوره اجرا
   شود.
3. گزارش‌های مالی با اسناد متناظر تطبیق داده شوند.
4. موجودی انبار، Batch، سریال و COGS در سناریوهای عادی و مرجوعی سازگار بمانند.
5. سناریوهای هم‌زمانی روی MySQL/MariaDB موفق باشند.
6. CI، Pint، PHPStan، type-check و build موفق باشند.
7. بررسی امنیتی مستقل انجام و ایرادهای بحرانی بسته شده باشند.
8. Backup/restore و rollback روی محیط production-like آزموده شوند.
9. UI دسکتاپ/موبایل و چاپگرها به‌صورت دستی پذیرش شوند.
10. مانیتورینگ، scheduler و queue worker در deployment فعال باشند.

## نقشهٔ آینده

### افق ۱ - رساندن MVP به نسخهٔ قابل انتشار

اولویت‌ها به ترتیب:

1. پذیرش دستی UI و رفع باگ‌های دیده‌شده
2. تست امنیتی و اصلاح ایرادهای بحرانی
3. First-run setup و lifecycle کامل کاربر
4. backup/restore، retention و deployment/rollback
5. تست واقعی چاپ و بسته‌بندی Print Agent
6. تست end-to-end روی MySQL با دادهٔ شبیه production
7. تگ نسخهٔ ۱ پس از پذیرش کاربر

معیار خروج: checklist تعریف پذیرش نسخهٔ ۱ کامل باشد.

### افق ۲ - تکمیل عملیات فروشگاه

1. تکمیل شمارش و تعدیل کالای سریال‌دار و Batch
2. مدیریت چند انبار در یک فروشگاه
3. ویرایش/لغو کنترل‌شده چک و گزارش اختصاصی چک
4. بهبود UX فرم‌ها، accessibility و واکنش‌گرایی
5. گزارش‌های تحلیلی بیشتر و بهینه‌سازی query در داده بزرگ
6. ابزارهای نگهداری، Audit alerting و مدیریت خطا

معیار خروج: فروشگاه بتواند عملیات روزانه را بدون مداخلهٔ فنی زنده نگه دارد.

### افق ۳ - نسخهٔ چندشعبه‌ای

چندشعبه‌ای نباید قبل از تثبیت نسخهٔ ۱ و اعتبارسنجی بازار شروع شود.
پیش‌نیازهای فنی:

1. ساخت `DocumentSequence` مستقل برای هر شعبه و سال مالی
2. scope کردن شمارش، انتقال، کاردکس و گزارش‌ها به شعبهٔ فعال
3. کنترل اتمیک آخرین شعبهٔ فعال
4. سیاست تخصیص کارمند به یک یا چند شعبه
5. active branch در session/context با control دسترسی نقش‌محور
6. گزارش تلفیقی و کنترل انتقال بین شعبه‌ها
7. migration و تست هم‌زمانی چندشعبه‌ای

معیار خروج: مرز داده، sequence، دسترسی و گزارش در سناریوی چندشعبه‌ای قابل
حسابرسی باشد.

### افق ۴ - یکپارچگی و کانال فروش

1. سامانه مودیان و صورت‌حساب الکترونیکی
2. اتصال فروشگاه آنلاین و مارکت‌پلیس
3. درگاه پرداخت و پوز
4. تطبیق بانکی و صورت‌حساب بانکی
5. پیامک و اعلان سررسید
6. import/export دادهٔ مهاجرت از نرم‌افزارهای رایج
7. API عمومی کنترل‌شده

هر اتصال خارجی باید idempotency، retry، outbox و لاگ قابل حسابرسی داشته باشد و
به transaction اصلی وابسته نماند.

### افق ۵ - گسترش ERP

پس از اثبات نیاز بازار:

1. دارایی ثابت
2. حقوق و دستمزد
3. تولید و مونتاژ
4. CRM و باشگاه مشتریان
5. بودجه و مراکز هزینه
6. پیش‌بینی و گزارش‌های مدیریتی پیشرفته

این موارد خارج از MVP هستند و نباید معماری فعلی را پیش از اعتبارسنجی بازار
پیچیده کنند.

## اولویت پیشنهادی مرحلهٔ بعد

مرحلهٔ فوری، توسعهٔ قابلیت جدید نیست؛ بستن پذیرش نسخهٔ ۱ است:

1. کاربر تست دستی UI/UX و سناریوهای کسب‌وکار را انجام دهد.
2. یافته‌های منطقی، امنیتی و رابط کاربری فهرست شوند.
3. فقط ایرادهای تأییدشده و در محدودهٔ توافق‌شده اصلاح شوند.
4. پس از پایدارشدن، First-run setup و user lifecycle تکمیل شود.
5. سپس backup/restore و deployment hardening انجام شود.
6. نسخهٔ ۱ تگ شود.

## روش کار با Agent

- ابتدا همین سند و سند معماری اولیه خوانده شوند.
- وضعیت Git و تست‌ها قبل از هر تغییر دوباره بررسی شوند.
- برای بررسی، ابتدا گزارش شواهد ارائه شود و تغییر بدون درخواست انجام نشود.
- برای اصلاح، دامنهٔ دقیق حفظ شود و قابلیت جدید ناخواسته اضافه نشود.

- هر تغییر باید تست متناسب و گزارش محدودیت‌ها داشته باشد.

- ادعای بررسی مرورگر، چاپگر فیزیکی یا production فقط با شاهد واقعی مجاز است.
